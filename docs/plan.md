# devsrv の進め方（figure-it-out の設計）

2026-10-07 に HANDOFF.md から始めた。ここに書くのは、完了の条件、範囲、厳しさ、段の並び。決定の記録は `.audit/devsrv.tsv`。

## 完了の条件（確かめられる形）

どれも `cargo test` の結合テストで、本物のプロセス（`python3 -m http.server` や `sh -c 'sleep …'`）を立てて確かめる。テストの状態の置き場所は一時ディレクトリにし、ユーザーの `~/.local/state/devsrv/` には触らない。

1. `devsrv start web --port auto --ready http -- python3 -m http.server {port}` が、1 行目に `http://127.0.0.1:<port>/` を出して 0 で終わり、その URL に HTTP で届く。
2. 起動してすぐ終了コード 3 で落ちるコマンドの `start` は 1 で失敗し、終了コード 3 とログの末尾を出す。
3. 動いているのと同じ名前の `start` は失敗し、動いているものの URL（か PID）と経過時間、`devsrv stop web` の案内を出す。前のものが落ちて記録だけ残っているときは、片付けて起動する。
4. `stop web` のあと、孫プロセス（`sh -c 'sleep 1000 & sleep 1000'` の中の sleep）まで消えている。`stop` を 2 回呼んでも 2 回目は失敗しない（もう止まっていると言う）。
5. 記録の PID が別のプロセスに使い回されている（起動時刻が合わない）とき、`stop` はそれを止めない。他人のプロセスは生き残る。
6. `wait port <空いているポート> --timeout 1` は 1 秒ほどで 1 で失敗する。`wait http://…` は応答があれば 0 で終わり、待った秒数を出す。
7. `who <port>` は、devsrv が起動したものなら名前を、そうでないものなら PID とコマンドを出し、どちらも止めない。
8. `ls` は名前、PID、ポート、経過時間、作業ディレクトリ、生きているかを出し、死んだものに印を付ける。`--json` でも同じ中身が出る。
9. `logs web -n 5` が末尾 5 行を出す。`--follow-until REGEX` は見つかれば 0、時間切れなら 1。
10. 別の作業ディレクトリ（git の top level）で同じ名前を使っても、ぶつからない。
11. `devsrv --help | head -40` に、書き方、主な使い方、出力、終了コードが入っている。
12. `devsrv start` が返ったあとも、呼んだシェルが終わっても、起動したプロセスは生きている（新しいセッションに切り離す）。

## 範囲

- Rust の 1 クレート、1 バイナリ。見込みは 1,500〜2,500 行（テスト込み）。サブコマンドは 6 つ（start、ls、logs、stop、who、wait）。
- macOS が主。Linux でも動くように書き、Linux でのテストは GitHub Actions（手動の workflow）に任せる。
- 範囲の外は HANDOFF.md のとおり（Orca・T3 の待ち、常駐管理、Docker、MCP）。

## 厳しさ: 高め

止めるべきでないプロセスを止めるのは取り返しがつかない。そこで次を関門にする。

- 止める・待つ・起動するの振る舞いは、どれも本物のプロセスを使う結合テストで確かめる（上の 1〜12）。
- 型と構成は architect（3 モデルの arena）で 2 案以上を比べて決める。
- 仕上げに interrogate（3 モデルの敵対的なレビュー）をかけ、「対応する」に入ったものを直す。
- 検証のスキル（`.agents/skills/verify-devsrv/`）で、実際に動かした証拠を残す。
